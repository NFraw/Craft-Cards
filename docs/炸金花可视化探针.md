# 炸金花 HUD 可视化探针

> 2026-10-21 实机复核校正：布局定稿以[棋牌游戏 HUD 布局与风格规范 v1](棋牌游戏HUD布局规范.md)为准。
> 当前探针为24阶段×4档GUI尺寸、1356项检查、78张线框图（新增准星避让规则）。它与实机一起使用320高共享画布，
> 并按完整卡牌模型宽10.2、高16换算；旧版“16:9”与“斗地主/炸金花相差14或28px”的解释已作废。
> `report.md` 与 `index.html` 是同一次探针的文本/图廊输出，不是两份独立游戏测试。
> 本轮真实联机与逐图查看结果见[测试报告](HUD统一与实机测试报告-2026-10-21.md)。

下文保留 WorkBuddy 初版探针的设计与问题发现记录；其中旧坐标、检查数量、牌面比例与“尚未做真实截图”的描述属于历史状态。

一个**不启动游戏**的独立测试程序：把炸金花 HUD 的每一种阶段、每一档分辨率下的
几何量算一遍，判一遍性质，再把结果画成线框图和 HTML 图廊。

解决的问题很具体：炸金花是后加的游戏，界面问题（选项压住卡牌、卡牌没贴底、
窄屏下按钮挤成一团、矮屏多人结算文字跑出格子）**只有开客户端打一局才看得出来**，
而且每次要重启 JVM、等两分钟。这个探针把"布局 / 排面 / 渲染设计"这一层从游戏里**摘出来**，
纯算术 + 纯 Java2D，一次跑完 96 个组合、1306 个检查点，约 2 秒。

## 一句话运行

```bash
./gradlew zjhUiProbe -PmcTarget=1.21.1 --offline
```

输出目录会打印在最后一行（多加载器工程里是 `build/mc-1.21.1/zjh-ui-probe/`）：

```
report.md            文本报告（逐组合 PASS/FAIL、与斗地主的对照、未通过项明细）
index.html           图廊 + 检查表，用浏览器打开
shots/*.png          78 张线框图
```

有 `FAIL` 时退出码为 1，可以直接挂 CI。

## 与斗地主的统一（设计语言）

这一版的核心工作不是"检查"，是**把两个游戏的 HUD 收成一套语言**。探针的作用是
把差异量出来、并在改完之后继续盯着。

### 抽出 `HudOptionBar`

此前选项行有三份实现：斗地主叫分是"固定 40px 一项、文字居中、焦点框右边界少 2px"，
炸金花是"按文字宽度算、文字左对齐、焦点框右边界多 2px"。同一个玩家在两局游戏里
看到的是两种东西。现在统一到 `common/.../client/HudOptionBar.java`：

| 维度 | 统一后 |
|---|---|
| 项宽 | **等宽**，取"最宽标签 + 12px"，下限 40px（斗地主四个两字标签正好各 40px，观感零变化） |
| 文字 | 项内**居中**（原来是左对齐） |
| 焦点框 | 选项左右各外扩 2px，**左右对称**（原来斗地主右边界少 2px） |
| 配色 | 白色普通 / 金色焦点 / 灰色禁用 / `0x66000000` 底衬，全部从 `HudOptionBar.COLOR_*` 取 |
| 提示行 | 选项行**上方** 13px（斗地主叫分原来在下方，与出牌阶段和炸金花相反） |
| 反馈行 | 提示行再上方 13px（炸金花原来画在屏幕顶部 y=46） |

### 竖向语法

两个游戏现在都遵守同一条链：

```
反馈行（红）    optionsY − 26
提示行（绿）    optionsY − 13
选项行          锚点
手牌            贴底
```

差别只剩**锚点**：斗地主用固定偏移 `h−165`（17 张牌铺满底部，位置不随牌数变），
炸金花贴着自己的手牌往上排（3 张大牌 + 一行手牌信息）。报告里的对照表直接给出每档分辨率的差值：

| 分辨率 | 斗地主选项行 y | 炸金花选项行 y | 差值 |
|---|---|---|---|
| 320×180 | 69 | 83 | 14 |
| 427×240 | 75 | 103 | 28 |
| 640×360 | 195 | 223 | 28 |
| 960×540 | 375 | 403 | 28 |

> 320×180 那一行原来是 **15 / 83（差 68）**——斗地主的固定偏移在最小档下算出 y=15，
> 正好压在 y=16 的阶段行上，提示行落到 y=2 盖住标题。这是探针跑出来的真实缺陷，
> 已由 `HudOptionBar.actionRowY` 的下限兜住（`minOptionRowY()` = 69），
> 正常屏幕上位置一点没变。

### 卡牌底边距

炸金花原来写死 24，斗地主是 `RenderConfig.hudBottomMargin`（默认 30）。
现在炸金花也取 30：`ZJHLayout` 存一份副本，`ZJHClient` 每帧从 `RenderConfig` 同步，
所以 `/craftycards reload` 改了配置，两个游戏一起动。

> 为什么存副本而不是直接读：`RenderConfig` 为了读写 `visual.json` 在静态初始化里建了 Gson，
> 而布局类要被纯算术单测和不出图的探针调用，不该因此背上 Gson/文件系统依赖。

## 它检查什么

检查分五组，全部只读 `ZJHLayout` / `HudOptionBar` / `ZJHControls` 的**真实**计算结果——
布局常数改了，报告里的数字跟着变，不存在"测试里抄一份常量"的漂移。

### 一、卡牌（排面）

| 规则 | 判据 |
|---|---|
| `cards-bottom-anchored` | 卡牌下沿恒等于 `屏高 − 底边距` |
| `card-aspect-16-9` | 布局高度与 `CardVisuals` 实绘的 `width×16/9` 一致（选中框/绿框才套得住牌） |
| `cards-do-not-overlap` | 三张牌互不重叠（间距 > 牌宽） |
| `cards-inside-viewport` | 整片手牌左右各留 ≥ 8px |
| `cards-centered` | 三张牌整体水平居中 |
| `cards-fit-height` | 卡牌上沿 ≥ 60，让开标题/阶段/局势/反馈四行 |

### 二、竖向节奏

`message-clears-header`、`message-above-hint`、`message-gap-shared`（间距必须等于
`HudOptionBar` 的共享常量）、`hint-above-options`、`options-above-hand-info`、
`hint-above-hand-info`、`hand-info-above-cards`。

### 三、选项行

`option-count`、`option-uniform-width`（等宽，与斗地主同一个排版）、
`option-inside-viewport`（含焦点框 ±2px 都在屏内）、`option-no-overlap`、
`option-min-hit-width`（每项 ≥ 10px 可点）、`option-label-fully-visible`。

### 四、结算页

`settled-block-centered`（整块垂直居中，与斗地主同一套）、`settled-header-above-rows`、
`settled-rows-clear-hint`（末行让开底部那行关闭提示）、`settled-row-fits-name`、
`settled-text-column-clear`（文字列不压牌列）、`settled-two-lines-inside-row` /
`settled-one-line-inside-row`、`settled-tight-net-visible`（一行模式先裁牌型、**不裁净得失数字**）。

### 五、阶段目录自洽

`ZjhUiProbeTest` 另外钉住：暗牌有「明牌」、三张全开后没有、暗牌比牌按 2 倍明注、
明牌后费用翻倍、等待开局只剩「离开牌局」、结算页没有选项行。

## 覆盖的阶段（24 个）

| 组 | 阶段 |
|---|---|
| 等待开局 | 加入即就绪 / 服务端给了原因（`waitingReason`） |
| 对局 | 暗牌第 1 轮 / 暗牌可比牌 / 明牌 1/3 / 2/3 / 3/3 / 大注（三位数费用）/ 封顶档（四位数费用） |
| 交互 | 选牌模式（无选项行）/ 比牌选目标（2、3、6 人局，以及 16 字符长 ID） |
| 结算 | 2–6 人 × 自己赢（有礼花）/ 自己输 |

## 覆盖的分辨率

| GUI 尺寸 | 对应窗口 | 说明 |
|---|---|---|
| 320×180 | 1280×720 + 缩放 4 | 原版允许的最小档，所有"挤"的问题都在这里暴露 |
| 427×240 | 1280×720 + 缩放 3 | 常见的低配档 |
| 640×360 | 1280×720 + 缩放 2 | 最常见的默认档 |
| 960×540 | 1920×1080 + 缩放 2 | 大屏档 |

## FAIL 与 WARN

- `FAIL` = 任何分辨率下都算缺陷，必须修，退出码 1。
- `WARN` = 极端窄屏下的可接受退化（例如 320×180 + 6 人局时目标名字被截断）。
  记在报告里，但不判失败——否则要么永远红，要么只能把这条规则删掉。

## 线框图是什么、不是什么

**是**：按 `ZJHLayout` / `HudOptionBar` 的真实坐标画的设计稿，颜色取自
`ZJHClient` 与 `HudOptionBar` 的调色板，所以"哪里空、哪里挤、哪一行压住了下一行"
与游戏里一致（像素位置已用 PNG 逐点核对过）。

**不是**：游戏截图。字体用系统雅黑（游戏用原版字体，字宽差 ≤ 1px/字符），
卡牌画成带点数花色的白框（游戏里是物品模型贴图）。

真实截图仍归 `pocSmoke` 那套四进程 harness（见 `docs/自动化验收.md`）。

## 这一轮跑出来并修掉的问题

1. **卡牌高度与实绘不一致**：`ZJHLayout.hand` 先由宽度定高、再把宽度夹回来，
   960×540 下 `height()=78` 而 `CardVisuals` 实际画 `width×16/9=76.4`，
   选中框和绿框都比牌高出一截，`bottom()` 也不再等于 `屏高−底边距`。
   改成"由高度反推宽度上限"，`height()==width*16/9` 恒成立。

2. **矮屏多人结算把净得失裁掉**：`resultRowHeight` 在 320×180 / 6 人时降到 14px，
   两行文字（牌型 + 净得失）会画进上一行里。改成行高 < 22px 时退成一行，
   并且**先裁牌型、后裁数字**——净得失的数字才是结算里唯一真正要看的信息。

3. **结算内容块贴顶**：两人局在 960×540 上只在顶部占 118px，剩 400 多像素全空，
   与斗地主的"整块居中"观感不一致。新增 `ZJHLayout.resultTop()`，整块垂直居中。

4. **斗地主操作块在 320×180 撞顶**：固定偏移 `h−165` 在最小档算出 y=15，
   压住阶段行、提示行盖住标题。新增 `HudOptionBar.actionRowY` 的下限兜底。

## 下一步（Stage B：真实截图）

探针覆盖的是"布局与渲染设计"。要在真实游戏里逐阶段截图，需要沿 `PocClient` 的路子
写一个 `ZJHPocClient`：单人客户端 + 命令方块摆一张牌桌 → 走完 等待 / 对局 / 明牌 /
选牌 / 比牌 / 结算 六个阶段，每阶段 `Screenshot.grab` 一张，然后对 PNG 做像素检查
（卡牌区域亮度、选项行是否有文字像素、结算遮罩是否存在）。
这一步要起一个服务端 + 一个客户端（不是四个），等布局探针稳定后再做。
