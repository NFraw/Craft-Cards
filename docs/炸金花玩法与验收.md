# 炸金花：操作与实机验收

目标：NeoForge 21.1.236 / Minecraft 1.21.1 / Java 21。客户端和服务端须同时使用本次 JAR（网络协议版本 4）。

## 开一桌

1. 从创造模式标签页取得“炸金花牌桌”，或用红地毯×1、木板×3、木棍×2合成（摆法与斗地主牌桌相同，替换地毯颜色）。
2. 未参局时 Shift+右键牌桌配置，任何附近玩家都可编辑，临时编辑锁防止同时修改。设置筹码物品、物品筹码开关、起局人数、底注、个人投入上限和行动时限并保存。未保存配置前不能加入；配置者不获得房主身份，也不必参局。
3. 每人右键加入。启用物品筹码时，需备够个人投入上限的筹码；默认底注1、上限40、起局3人、行动30秒。服务器筹码总闸门关闭时使用虚拟注额。
4. 加入即就绪，达到配置的起局人数后服务端自动检查距离与预算、托管筹码并发牌，无需准备或开始按钮。例如设为6人，第6人加入才自动开局。等待者走远或筹码不足时显示原因；返回或补足后自动重试开局。

## 回合操作

### 筹码兑换（后续源码修改，尚未更新安装包）

本桌筹码选铁锭、金锭或钻石时，所有金额均以所选物品为1单位；普通铁块、金块、钻石块分别计为同材质的9单位。其他筹码仍按原物收付，不跨材质兑换，也不自动识别其他模组物品的价值。

例如只带5个铁块可通过40铁锭预算审核：服务器兑换出40单位托管，找回5个铁锭；结算按实际投入与所得精确收付。发还的普通基础筹码每9个换成1块，不足9的余额以基础物品发还。自定义基础筹码保留名称、附魔等组件，不压缩；带非默认组件的方块不作为可拆换面额。背包放不下的找零或结算物品沿用掉落返还路径。

普通方块兑换由所选基础筹码决定，白名单仍校验本桌所选筹码。选择“铁块”作为本桌筹码时，单位仍是铁块，不反向把零散铁锭当成小数筹码。钞票本次未添加；若后续新增，每张9块对应81基础单位，需同时注册物品、面额与兑换测试。

斗地主也使用同一兑换组件。规则金额、封顶或最高档追注轮数与面额换算分开处理；本次兑换修改不决定尚未确认的三轮收尾条件。

以下为回合操作：

- 暗牌时同时显示五个按钮：明牌、跟注、加注、加注翻倍、弃牌。滚轮选择按钮，右键牌桌确认；不可用的加注档仍显示但变灰。
- 仅本人回合选择“明牌”后进入选牌模式，滚轮定位、左键选中，再右键牌桌翻开所选牌；右键空气返回行动区。选择入口本身不改变明暗状态。
- 翻开一张或两张后，仍保留“明牌”入口；翻牌确认后返回行动区，重新选择“明牌”可继续选择未翻牌，焦点默认落在第一张未翻牌上。仅三张全部翻开后撤掉“明牌”，剩下跟注、加注、加倍、弃牌四项。首次实际翻牌后，三个收费项立即按明注刷新，继续翻牌不会再次翻倍。
- 翻一张就转明牌，跟注额翻倍；未翻的其他牌仍为牌背。翻牌不扣款、不结束回合、不重新计时。同一次右键只翻牌，不同时下注；等待确认后再选择行动。
- 「明牌」入口**只要还没翻满三张就一直存在**：可以一回合内分几次翻，也可以隔几个回合再翻，翻满 3/3 才撤掉这个选项；已翻开的牌位不能再被选中。
- 跟注：暗牌付当前暗注基准 B，明牌付 2B。加注档位是底注的1/2/4倍，只能调高，按本人明暗状态扣一次费用。
- 前两整轮不能比牌；第三轮起选择任一其他在局者，支付自己当前跟注费用的两倍，目标不付费。平手发起者输，比牌结束即换人，输家出局。
- 主动弃牌、超时、离开或掉线丧失已投入锅底的部分，不额外赔款；Shift+右键牌桌离开。未下注预算退还。
- 个人累计投注达到上限即系统开牌；下一笔合法付费会超过上限时，不扣这笔钱而直接开牌。这是当前采用的简化封顶规则。
- 牌型为豹子、顺金、金花、顺子、对子、散牌、特殊235。顺子 QKA > A23 > KQJ > … > 234；特殊是至少两种花色的235，平时最小，参比者中同时有豹子时特殊胜。出局者不重新参加系统开牌。同花235仍为金花。
- 剩一人则该玩家赢锅底；系统开牌同牌同点并列平分，余数按庄位起的座位顺序分配。没有喜金、抽成、额外奖励、all-in或边池。

## 画面对应关系

本人三张手牌固定在 HUD 最下方（下沿让开快捷栏）；手牌信息、选项行、提示行依次叠在卡牌上方——卡牌永远是屏幕上最下面的东西。顶部显示轮次、行动者、倒计时、锅底和上限。没有侧边六人列表。

其他玩家身前三张立牌显示公开状态：未翻为牌背，已翻的数量用 `card_empty.png` 替换。1/2/3张空牌都属于明牌，费用倍率一样。左侧为累计投入，右侧为最近行动；行动者显示“行动中”，庄家名称上方显示金黄色 `[ 庄 ]` 标记。出局后三张世界牌消失，替换为“出局”。真实牌面在局中不会发给对手，绕背观察也看不到。

结算 HUD 仅展示所有原始参局者的三张真实牌、牌型与净得失，包含弃牌、比牌出局、离开和掉线者。

结算成功后服务端发送全员结果并自动退局、释放牌桌。客户端只保留一份结果供查看，底部没有离开、重开或滚轮选项；右键任意位置（包括空气）只关闭本地结果，不发送离开请求。有人继续看结果时，其他人也能加入新的牌局，新旧会话不会互相改写状态。

- 再玩需要关闭结果后重新右键加入，达到配置人数自动开局，不提供快速重开。
- 牌桌取消退款不会公开未结束的手牌。

## 第二轮修订：界面风格统一 + 对局生命周期（2026-10-21 15:00）

按用户实机反馈（"选项风格与斗地主不一致""结算后没有完整退出机制，玩家卡在对局里退不出来"）修改：

- **视觉统一**：HUD 改成与斗地主同一套语言——白色居中标题、灰色阶段行（倒计时按紧迫程度变色）、绿色操作提示、选项是纯文字 + 金色焦点 + 深色底衬（删掉原来的灰框按钮）。结算从"内嵌深色面板"改为整屏半透明遮罩 + 礼花，礼花抽成 `HudConfetti` 由两个游戏共用。
- **结算生命周期**：结算底部新增选项行「再来一局」（房主）/「离开牌局」，滚轮选择、右键确认；默认焦点落在「离开牌局」，避免误触重开。`再来一局` 回到准备大厅并保留椅子，所有人需重新准备。
- **退不出来的三个根因**：
  1. 结算只提供"右键退出"，没有任何重开路径 → 现在有明确的选项行，且 `tick()` 对 LEAVE 做了 3 秒无回执的本地收尾，任何情况下都不会把玩家钉在遮罩上；
  2. 房主在结算离开后房主位仍指向他，剩下的人谁都不是房主、开不了下一局 → 离开即空出房主位，`ownerPresent()` 判断"房主是否还坐在桌上"，其余人可直接接手；
  3. 最后一人离开后会话仍停在 SETTLED → 全员离开即自动回到等待状态，空会话由 tick 回收，新玩家能重新加入。
- **配置入口与斗地主对齐**：空桌时任何附近玩家都能 Shift+右键配置（一把临时编辑锁防冲突），不再把非房主静默转成观战。

自动化验证：157 项单元测试通过（新增选项行排版 3 项），69 项服务端 GameTest 全部通过（新增"房主离开后他人接手开局""全员离开回到等待""再来一局保留椅子且需重新准备""空桌任何人可配置"4 项）。安装 JAR 585,469 字节，SHA-256 `1FDAFC800685B1FF72D41C8579FAA9B22338263638B8A60D22A56AED68CF0A90`。真实客户端与多客户端对局仍由用户验收。

## 第三轮：明牌可重复 + 结算重复右键修复

- **「明牌」改为可重复**：原来用布尔 `looked` 判断，翻开第一张就把入口删了，剩下两张再也翻不了。现在按已翻张数决定：只要还没翻满 3/3，「明牌」就一直在，可以逐张翻、也可以分几个回合翻，翻满才撤掉。
- **结算后反复右键桌子**：`ZJHSession.handle` 的 JOIN 无条件调用 `resetLobby()`，任何人右键一次就会把所有人的结算画面掀回大厅；同时客户端 `busy()` 在包丢失时永不清零，表现为"右键没反应"。现在结算期有人时 JOIN 直接拒绝（"本局已结束，等房主开下一局"），任何动作 5 秒无回执即解除等待，离开后 0.8 秒内的误点不再触发重新入座。
- **「自动底牌」（封顶收尾）**：实现位于 `ZJHEngine.pay()/raise()/compare()`，与已确认的简化方案一致——达到上限立即系统开牌；下一笔会超限时不扣款直接开牌。该笔超额支付是刻意免费的，不是漏扣。

## 第五轮：与斗地主的 HUD 设计语言统一（2026-10-21 19:40）

按"查一下斗地主的真实布局和这个设计一不一样，我需要统一这个设计语言"逐项核对并统一：

- **抽出 `HudOptionBar`（两个游戏共用）**：选项行原来有三份实现——斗地主叫分"固定 40px 一项、文字居中、焦点框右边界少 2px"，炸金花"按文字宽度算、文字左对齐、焦点框右边界多 2px"。现在统一为**等宽项 + 项内居中 + 左右对称的金色焦点框 + 共享配色**。斗地主四个两字标签仍是每项 40px、总宽 160，观感零变化（`HudOptionBarTest.ddzBidRowKeepsItsExactPreviousGeometry` 钉住）。
- **竖向语法统一**：反馈行（红）→ 提示行（绿）→ 选项行，间距 13/13 由 `HudOptionBar.hintY/messageY` 统一给出。斗地主叫分的提示行原来在选项行**下方**（与它自己的出牌阶段、也与炸金花都相反），已移到上方；炸金花的反馈行原来在屏幕顶部 y=46，已移到操作块上方。
- **卡牌底边距统一**：炸金花原来写死 24，斗地主是 `RenderConfig.hudBottomMargin`（默认 30）。现在炸金花默认 30 且每帧同步该配置，`/craftycards reload` 改了两个游戏一起动。`ZJHLayout` 存副本而非直接读 `RenderConfig`——后者静态初始化要建 Gson，不该让纯算术单测和探针背上这个依赖。
- **探针顺带查出斗地主一个真缺陷**：固定偏移 `h−165` 在 320×180 下算出 y=15，正好压在 y=16 的阶段行上，提示行落到 y=2 盖住标题。已由 `HudOptionBar.actionRowY` 的下限（`minOptionRowY()` = 69）兜住，正常屏幕上位置一点没变。
- **剩下的差别只有一个**：操作块锚点。斗地主固定 `h−165`（17 张牌铺满底部，位置不随牌数变），炸金花贴着手牌往上排（3 张大牌 + 一行手牌信息）。探针报告给出每档分辨率的实际差值：320×180 是 14px，其余三档 28px。
- 验证：177 项单元测试、81 项 GameTest 全部通过；探针 1306 个检查点全 PASS。真实客户端观感仍由用户验收。

## 最新开局规则修订（仅源码，尚未重新打包）

取消房主制、准备按钮、手动开始以及房主再来一局。上文历史构建记录里的房主/准备流程属于旧版本；当前操作以本节及「开一桌」为准。

牌桌第一次保存配置后才开放入局，加入即就绪，达到配置起局人数自动开局。配置者不需要入座；临时编辑锁只防并发修改。等待者不在范围或预算不足时显示原因，条件恢复后每5刻检查并自动开始。结算发送完整结果后自动释放全部座位和会话，客户端可继续查看本地结果，不阻碍其他人加入新局；再次加入满人自动开始下一局。

开局前完整校验所有人的预算，物品托管失败沿用原有回滚；旧 READY/START/LOBBY 编码保留但不再接受这些操作，不能绕过人数条件或清除其他人的结算。
