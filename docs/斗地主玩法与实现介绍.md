# 斗地主（三人联机）玩法与实现介绍

> 最后更新：2026-09-14
> 适用版本：NeoForge 1.21.1，Java 21
> 本文是斗地主的历史玩法说明，其中较早的筹码与观战交互描述可能已过时。当前操作以 [README](../README.md) 为准。
> 本文档介绍斗地主的**玩法**、**交互操作**、**规则实现**、**联机架构**与**配置**，玩家与开发者共用。
> 开发约定与踩坑记录见 [AGENTS.md](../AGENTS.md)，音频包格式见 [音乐包格式.md](音乐包格式.md)。

## 一、玩法概述

斗地主是模组内置的三人卡牌游戏，**只支持联机**（没有单人模式、也没有 AI 对手）。
三名玩家在同一张牌桌入局后自动开局：发牌 → 叫地主 → 出牌 → 结算。

**一句话流程**：

```
合成并放置斗地主牌桌 → 声明本局筹码 → 3 人右键入局 → 满员自动发牌（每人 17 张 + 3 张底牌）
→ 叫地主（不叫 / 1分 / 2分 / 3分）→ 地主收底牌先出 → 轮流压牌 / 过牌
→ 某家出完手牌 → 结算（地主赢或农民赢）→ 从背包实付筹码 → 点击关闭
```

**牌桌**：`crafty_cards:ddz_table` 是**单个方块**（1×1 格），合成配方为
上一行中间一块绿色地毯、中间一行三块木板（任意 `minecraft:planks`）、下一行左右各一根木棍。

**没有座位实体**。入局后玩家**自由走动**，不需要坐下、也没有"下马离开"。
座位只是逻辑编号（0/1/2），用来决定回合顺序，不对应桌面上的固定方位。

## 二、交互操作指南（玩家手册）

斗地主界面**不是全屏 GUI**，而是叠加在主世界上的 HUD 信息层，牌桌周围的世界始终可见。
所有操作都是右键牌桌 / 滚轮 / 鼠标左右键，不需要打开任何界面。

| 操作 | 效果 |
|------|------|
| **潜行 + 手持筹码物品 + 右键牌桌** | **声明本局筹码**（用手里这件物品下注）。未声明的牌局不能入局；一旦有人入局或开局就锁定。`chipsRequired = false` 的娱乐桌跳过这一步 |
| 右键牌桌（未入局，筹码已声明且备足） | 加入牌局；入局时**收 1 个筹码进物品池** |
| 右键牌桌（牌桌已满 3 人） | 切换**观战**（只读，能看不能操作） |
| 滚轮（叫分阶段，轮到自己） | 在【不叫 / 1分 / 2分 / 3分】之间循环，当前选项金色高亮 |
| 右键牌桌（叫分阶段，轮到自己） | 按滚轮所选分数确认叫分 |
| 滚轮（出牌阶段） | 移动手牌焦点（黄色边框）。**方向与滚轮相反**：向上滚左移、向下滚右移。不切物品栏，**非回合也能预选** |
| 左键（出牌阶段） | 把焦点牌加入 / 移出选中集合（选中牌上移） |
| 右键**空气**（准星不指牌桌） | **取消全部选中**（比不过时一键清空，也防误破坏方块） |
| 右键牌桌（出牌阶段，轮到自己，有选中牌） | 出牌（本地先预检牌型，无效会提示"无效的牌型"） |
| 右键牌桌（出牌阶段，轮到自己，无选中牌） | 过牌；**新一轮牌权不能过**，会提示先出牌 |
| **Shift + 右键牌桌**（参局者） | **离开牌局**：退还筹码、归还扑克牌，牌局随即解散 |
| **Shift + 右键牌桌**（未入局、空手） | 开启 / 停止观战（需站在入局距离内） |
| 点击任意处（结算界面） | 关闭结算界面 |

**手牌要先握牌**：只有主手握 **`crafty_cards:card`（扑克牌）** 时才会展开手牌并可出牌——
切到武器只收起牌面，牌局照常进行。HUD 在未握牌时会提示"握上斗地主扑克才能出自己的牌"。

**预选机制**：出牌阶段无论是否轮到你，都可以提前用滚轮 + 左键挑好要出的牌；
轮到你时右键牌桌确认出牌，比不过时右键空气一键清空，再右键牌桌过牌。

**HUD 信息布局**（自上而下）：

| 位置 | 内容 |
|------|------|
| 顶部居中 | 标题"斗地主" + 阶段行（等待中 / 叫地主 / 出牌中 / 结算）与回合提示 |
| 顶部下方 | 筹码与押注信息（本局筹码物品、底注、预计输赢份数） |
| 顶部下方 | 地主行（金色显示地主是谁） |
| 左上 | 底牌（开局后可见，3 张） |
| 右侧 | 上家出的牌（真实牌面模型）+ 牌型与出牌人标注 |
| 底部 | 自己的手牌（扇形展开、选中上移）+ 操作提示 + 提示消息 |

## 三、筹码与结算

### 3.1 筹码由玩家声明

本局用哪种物品下注**由玩家声明**，不是模组替你猜：第一个声明的人定下本局筹码，之后锁定。
可用物品是白名单（`server.json` 的 `chipItems`，默认钻石 / 金锭 / 铁锭 / 绿宝石 / 下界合金锭），
支持其他模组的物品。

- **未声明筹码不允许入局**：先潜行 + 手持筹码右键牌桌声明。
- **入局门槛**：背包里必须备足**门槛**个筹码才允许入局。默认门槛 = `max(1, 底注) × 6`
  （叫分上限 3 × 地主两倍份数 × 底注 = "无炸弹时最坏的一局"）；房主也可以用 `server.json`
  的 `chipEntryCount` 直接指定（`0` = 自动，界面档位到 100 万），高额桌与宽松桌都能开。
  不足会明确提示还差多少；手动值低于派生值时界面会提示"输家可能赔不出"（结算少赔并提示）。
- 入局时**收 1 个筹码进物品池**，用 `ItemStack.split(1)` 取出，
  **附魔 / 自定义名等组件原样保留**，结算或退还时交还原物——绝不会用 `new ItemStack` 重建。
- **不需要筹码的娱乐桌**：`server.json` 的 `chipsRequired = false` 时整条筹码链路关闭——不必声明、不校验背包、入局不收押注、结算不转移任何物品（`requiredChips()` 返回 0，界面也据此切成"不需要筹码"）；关掉之后再声明筹码会被明确拒绝。

### 3.2 结算：底分 × 倍率

按市面上常见的斗地主规则计分，**每名农民应付的份数**为：

```
perFarmer = 底分（叫分 1/2/3） × 倍率 × 底注（server.json 的 chipStake，默认 1）
倍率 = 2^(炸弹数 + 火箭数)，春天或反春天再 ×2
```

- **春天**：地主获胜且两名农民一张牌都没出过 → 倍率 ×2
- **反春天**：农民获胜且地主只出过一手牌（≤1 次出牌）→ 倍率 ×2

结算顺序是**押注池优先**：输家押在池子里的原物（附魔等组件完整）先被交给赢家，
不足的部分才从他的**背包**补取；赢家自己那份押注最后原样退还。总量守恒——不会凭空生成，也不会静默销毁物品。
顺序不能反过来（先退还押注、再从背包赔付）：那样池子会被清空，而赔付只认结算时刻的背包，
输家只要在结算前把筹码塞进箱子或丢在地上就一分不赔。实在取不到足够的筹码时，会收到"筹码不足，本次少赔 N 个"的提示，赔多少算多少
（这是"用实物结算倍数赌注"的固有限制，入局门槛就是为了让常见牌局不至于赔不起）。

**中途解散**（有人离开 / 掉线 / 拆桌 / 空闲超时）时**全额退还**三家的押注，不做赔付。

## 四、规则实现（引擎）

核心逻辑在 `game/DDZEngine.java`——**纯 Java 引擎，不依赖 Minecraft 环境**，可直接单测。

### 4.1 卡牌编码（54 张）

| 编码 | 含义 |
|------|------|
| 0–51 | 标准 52 张：`id / 4 + 1` = 牌面（1=A，2-10，11=J，12=Q，13=K）；`id % 4` = 花色（0=♠，1=♣，2=♦，3=♥） |
| 52 | 小王 |
| 53 | 大王 |

**牌力等级**（`getRank`）：A=14，2=15，小王=16，大王=17；其余为牌面值本身。
**每张牌 ID 全副唯一**，同一局中不可能出现两张相同的牌（引擎会逐张从手牌副本中扣减，拒绝重复声明）。

### 4.2 支持的全部牌型

| 牌型 | 判定要点 |
|------|----------|
| 单张 | 1 张（含单张王：小王 rank 16、大王 rank 17，都比 2 大） |
| 对子 | 2 张同点 |
| 三条 | 3 张同点 |
| 三带一 | 4 张 = 三条 + 任意 1 张 |
| 三带二 | 5 张 = 三条 + 一对 |
| 顺子 | ≥5 张连续单牌，**max rank ≤ 14（不含 2 和王）** |
| 连对 | ≥3 对连续对子（≥6 张） |
| 飞机 | ≥2 个连续三条 |
| 飞机带单 | 飞机 + 每个三条带 1 张单牌 |
| 飞机带对 | 飞机 + 每个三条带 1 对 |
| 四带二(单) | 6 张 = 四条 + 2 张单 |
| 四带二(对) | 8 张 = 四条 + 2 对 |
| 炸弹 | 4 张同点 |
| 火箭（王炸） | 小王 + 大王 |

**压牌规则**（`playCards` 比较主 rank）：

- 同牌型、同张数才可压，主 rank 大者胜；顺子 / 连对 / 飞机取**最大**的那张比较
- **10-J-Q-K-A 是合法的最大五连**（A=14 > K=13），已用单测固定住
- 三带一 / 三带二 / 飞机 / 四带二的主 rank 是**三条或四条**的 rank，带牌不参与比较
- 炸弹可压任意非炸弹牌型；炸弹之间比主 rank
- 火箭压一切，且不能再被压
- 单张王只能当单张出，两张王才是火箭

### 4.3 叫地主

- 发牌后随机指定一名玩家先叫，轮流叫分
- 每个玩家可叫【不叫 / 1分 / 2分 / 3分】，叫分必须**严格大于**上家叫分
- 叫 3 分直接定地主；三轮叫完有最高分者定地主；**三轮都无人叫则重新洗牌发牌**
- 地主获得 3 张底牌，牌局开始，地主先出

### 4.4 出牌与胜负

- 轮流出牌；**两家连续过牌**后原出牌人获得新一轮牌权，新一轮牌权**必须出牌、不能过**
- 某家手牌出空即结束，进入结算
- 胜负判定（`getWinnerTeam`）：地主手牌出空 → 地主赢；否则 → 农民赢（返回 `-2`）
- 结算时服务端统一清退三家，但快照保留，故结算界面仍能展示三家完整剩余手牌

## 五、联机架构（开发者）

### 5.1 总体设计

**服务端权威引擎 + 全量状态快照同步**。

```
┌──────────────────────────┐         ┌──────────────────────────┐
│        客户端（3 台）       │         │          服务端           │
│                          │  C2S    │                          │
│  ClientDDZData（缓存快照） │ ──────► │  DDZTableManager（单例）  │
│  DDZGameHud（HUD 渲染）   │  JOIN/  │   Map<TableKey,DDZSession>│
│  WorldHandCards（立牌）    │  BID/   │  DDZSession（3 座位+引擎） │
│  WorldPlayedCards（出牌）  │  PLAY/  │  DDZEngine（权威规则）     │
│                          │  PASS/  │                          │
│                          │  LEAVE  │  S2C 全量快照（每人独建）   │
│                          │ ◄────── │  GameStatePayload        │
└──────────────────────────┘         └──────────────────────────┘
```

- **所有牌局逻辑只在服务端 `DDZEngine` 执行**，客户端是纯"显示器"
- 每次操作后服务端为同桌的每个人**单独构建**一份全量快照（`myIndex`、`myHand`、`visibleHands`
  因人而异），再用 `PacketDistributor.sendToPlayer` 逐个发，不共用同一 payload 广播
- 客户端收到快照即刷新 `ClientDDZData` 缓存，HUD / 世界渲染读取缓存自动更新

### 5.2 网络协议（NeoForge payload）

| 方向 | Payload | 内容 |
|------|---------|------|
| C2S | `PlayerActionPayload` | `TableKey` + `Action{JOIN,BID,PLAY,PASS,LEAVE,DECLARE_CHIP,WATCH}` + 叫分 `score` + 出牌 `cards` |
| S2C | `GameStatePayload` | 全量快照：桌标识、我的座位、三家名字 / 剩余数 / 在线、阶段、地主、当前回合、叫分、上家出的牌与牌型、底牌、我的手牌、三家完整手牌、各座位可见牌面、胜负、是否解散、押注与筹码信息、提示消息。NBT 序列化 |

**`TableKey`** = `维度 + 方块坐标`，跨维度唯一标识一张桌。

**两条硬性约定**（踩过坑，违反会静默错位或崩服）：

- 网络动作枚举**只能往末尾追加**——`writeEnum` 按 ordinal 编码，插在中间会让动作号错位
- payload handler 内必须 `context.enqueueWork()` 回主线程再操作 manager / engine

### 5.3 服务端会话生命周期（DDZSession）

| 事件 | 处理 |
|------|------|
| 声明筹码 `DECLARE_CHIP` | 服务端读**主手**物品（包里不传物品 id）、校验白名单与距离，锁定本局筹码 |
| `JOIN` | 校验筹码已声明、在 `joinRadius` 内、背包筹码 ≥ 门槛 → 收 1 个进池、分配空位（`chipsRequired = false` 时这三项校验与收池全部跳过）；**满 3 人自动发牌开局**；桌已满则切换为观战 |
| `WATCH` | 未入局玩家的观战开关（需在 `joinRadius` 内），开启后不受距离限制持续收到只读快照 |
| `BID` / `PLAY` / `PASS` | 先校验"当前回合 == 本人座位"；PLAY 再校验手牌包含性与牌型合法性（引擎双保险） |
| `LEAVE`（Shift+右键） | 退筹码、还牌、清座位；游戏中则解散整桌 |
| 玩家掉线 | 走同一条 `handleLeave` 路径（等待中清位，游戏中解散） |
| 牌桌被拆 | `BlockEvent.BreakEvent` → 解散整桌 |
| 空闲超时 | `idleTimeoutTicks`（默认 10 分钟）无操作 → 解散 |

**解散路径必须逐个通知**：任何把会话从管理器移除的路径，都要先给"还会看这个界面的人"发一份
`sessionClosed` 快照——包括不占座位的观战者，也包括**刚刚离开的那个人**。
`handleLeave` 曾经是"先清座位、再解散"，而解散只遍历座位表，导致离开者的客户端收不到任何
终止快照、永久停在牌局界面上，且会话已移除、拆桌也没有反应（表现为"牌局关不掉"）。
现在改为**清座位之前**先给他发一份"你离开了牌局"。

### 5.4 防作弊：牌面可见性由服务端决定

服务端构建每份快照时按 `game/DDZVisibility`（纯函数，有单测）决定 `visibleHands`：

| 观察者 | 看自己 | 看他人牌面 |
|---|---|---|
| 对局参与者 | 否（自己的牌在 HUD，世界里不重复渲染） | `participantsSeeCards`，**默认关** |
| 旁观者 | 无自己的牌 | `spectatorsSeeCards`，**默认开** |

客户端只拿得到服务端下发的牌面，拿不到就只渲染牌背——**能不能看牌完全由服务端说了算，
不依赖客户端自觉**。

## 六、客户端渲染

### 6.1 HUD 叠加层（`client/DDZGameHud`）

通过 `RegisterGuiLayersEvent.registerAboveAll` 注册为叠加在所有界面之上的 HUD 层（非全屏 Screen）。
卡牌用真实 3D 物品模型渲染：手牌扇形展开、选中上移、焦点黄色边框；上家出的牌与底牌用小号牌行。
布局见第二章表格。

### 6.2 世界内立牌（`client/WorldHandCards`）

在 `RenderLevelStageEvent.AFTER_TRANSLUCENT_BLOCKS` 阶段渲染**各参局玩家身前**的一排立牌，
跟随该玩家位置与视线（`forward × handForwardDist`、胸口高度），牌面朝向持牌人：
他自己看牌面，对面看牌背，旁观者站到他身后能看到牌面。**自己不渲染**（HUD 里已有）。

### 6.3 桌面出牌（`client/WorldPlayedCards`）

上家出的牌平铺在桌面上（带叠放厚度），与 HUD 右侧的牌型标注对应。

## 七、配置与命令

| 文件 | 归属 | 内容 |
|------|------|------|
| `config/crafty_cards/visual.json` | 客户端 | 渲染参数（HUD 手牌 / 世界立牌 / 桌面出牌 / 筹码悬浮高度） |
| `config/crafty_cards/sounds.json` | 客户端 | 总开关、音量、音乐包选用（BGM 声道与是否压低原版音乐只能手改） |
| `config/crafty_cards/soundpacks/<id>/` | 客户端 | 玩家自建音乐包（`pack.json` + `*.ogg`） |
| `config/crafty_cards/server.json` | 服务端 | 玩法开关：是否需要筹码、入场底注、**入局门槛**、观战可见性、
参与者互看、观战半径、观战快照补发间隔、空闲超时、入局距离、筹码白名单 |

**游戏内配置界面**（Mods 列表 → Crafty Cards → Config，或 `/craftycards config`）
是"主页 → 分类页"的多层级结构，主页每项后面直接写着当前状态：

```
设置主页
 ├─ 音乐包        总开关 · 音量 · 选用哪个音乐包 · 重新扫描 · 包列表
 ├─ 玩法设置（房主） 是否需要筹码 · 入场底注 · 入局门槛 · 入局/观战距离 · 空闲超时 · 看牌权限
 └─ 渲染参数      手牌大小/间距/扇形 · 立牌距离与高度 · 出牌缩放 · 筹码高度
```

音频只剩「音乐包」一项入口：游戏侧能改的只有总开关、音量与选哪个包；
**逐键指派文件、逐条调权重、试听这些"在游戏里直接改音频"的操作已全部去除**——
音频只有音乐包这一个接入接口。选包/音量共用一份编辑会话，
关闭设置界面时若还有未保存的改动，会先问一次，不会静默丢弃。

**命令**：

| 命令 | 作用 |
|------|------|
| `/craftycards config` | 打开设置主页（多层级入口） |
| `/craftycards sounds` | 直接跳到「音乐包」页 |
| `/craftycards play` | 直接跳到玩法设置页（房主参数） |
| `/craftycards render` | 直接跳到渲染参数页 |
| `/craftycards reload` | 重载渲染参数文件（`visual.json`），下一帧生效 |

**公共服务器建议**：把 `spectatorsSeeCards` 设为 `false`，保持 `spectateRadius` 为 `0`——
否则任何走到桌边的人都能看到三家手牌。

## 八、音频（音乐包）

- **模组不含任何音频**：音效与 BGM 全部来自**音乐包**。仓库附一份 `soundpacks/官方默认包/`
  （4 段 BGM + 48 条牌型播报 + 炸弹/过牌语音），复制到
  `config/crafty_cards/soundpacks/` 后在 **配置 → 音乐包** 页选它即可。
- 音频以 **61 个音频键**为单位（7 音效 + 6 BGM + 48 牌型语音）。一个键可以配**多个文件**，
  各带权重，播放时按权重随机挑一个——"不要"准备三条就三种说法。
- BGM 除了按阶段（等待 / 对局 / 结算胜负），还会跟着**场上形势**换：有人只剩 **3 张以内**时放
  「残局」，**王炸**打出来后放「王炸之后」（火箭没人压得住，所以它持续到下一轮重新出牌）。
  这两首没配的文件包会自动退回「对局进行中」，不会变成没声音。
- 牌型语音优先于通用出牌音效；某个牌型没有文件时才用通用出牌音效，都没有则原版音效。
- 权重（哪条声音更常出现、想不要哪条）都写在**包的清单里**，用制作程序调；
  游戏内只在 **配置 → 音乐包** 里选包、调总开关与音量，不提供逐键/逐文件的自定义操作。
- 做包用 **`tools/soundpack_maker.py`**（可视化 GUI，`--cli` 为命令行模式）；
  包只能由它修改，游戏内只读取与选用。格式见 [音乐包格式.md](音乐包格式.md)。
- 播放 BGM 时把原版背景音乐压低到 10%（可配），BGM 停止后自动还原；
  因此 BGM 声道默认是"玩家"而不是"音乐"（同声道会把 BGM 一起压掉）。
- 音效由**快照差异**驱动（服务端只发状态、不发音频指令），重复下发不会连播。

## 九、测试与验证

```bash
.\gradlew.bat test              # 112 个单元测试
.\gradlew.bat runGameTestServer # 23 个 GameTest（牌桌、会话、筹码、快照可见性、端到端、免筹码局）
```

单元测试的类路径上**没有 Minecraft 的类**，所以可单测的类必须不引用 MC 类型
（`DDZEngine`、`DDZGeom`、`DDZVisibility`、`DDZInteraction`、`CustomAudio`、
`ClientSnapshotPolicy`、`Hud*Layout` 系列都是纯 Java）。

**单测覆盖**：发牌（54 张、每人 17 + 底牌 3）、叫地主（含无人叫重发）、全部牌型判断
（含 10-J-Q-K-A 压 9-10-J-Q-K）、出牌验证、炸弹 / 火箭互压、大小王、胜负判定、
倍率与春天 / 反春天、快照 NBT 序列化往返、可见性规则、音频槽位契约。

**GameTest 覆盖**：多人入局与自动发牌、观战开关、附魔筹码原样返还、距离校验、
**服务端按接收者构建快照**（参与者的他人牌面必须为空、旁观者必须拿到三家牌面）、
数据包（配方 / 掉落表 / 碰撞箱）、端到端一局。

**GameTest 验证不到的部分**：模拟玩家的连接不是真实客户端，向它发自定义 payload 会抛
`Payload ... may not be sent to the client!`，所以"快照真的送到了客户端"这类只能靠人眼在
游戏里验收（交付测试报告见 [验证与已知边界](open-source/TESTING.md)）。
