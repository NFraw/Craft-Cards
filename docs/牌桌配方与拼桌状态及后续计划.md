两份配方已经分开，炸金花使用红色地毯；上一轮改桌布时没有同步修改斗地主配方，因此其绿色材料与深蓝外观存在不一致。不能表述为“配方已全部按新配色改完”。

当前合成摆法相同，空格为空槽：

```text
 C 
PPP
S S
```

`C` 为对应地毯，`P` 为木板，`S` 为木棍。

### 查询依据

- 实际配方：`common/src/main/resources/data/crafty_cards/recipe/blocks/ddz_table.json`、同目录 `zjh_table.json`。
- 斗地主：`BlockDDZTable`、`DDZTableLayout`、`DDZTableStructure`、`DDZTableManager` 以及 `blockstates/ddz_table.json` 已构成拼桌链路。详细规则见 [多方块牌桌](多方块牌桌.md)。
- 炸金花：`BlockZJHTable` 没有四向连接属性及邻接结构处理；`ZJHTableManager` 直接以 `payload.table()` 查询或创建会话，拆桌也只移除该坐标会话。
- `blockstates/zjh_table.json` 只有单一模型变体。`models/block/zjh_table.json` 虽继承斗地主基础几何并覆盖酒红贴图，但继承基础模型不等于具备拼桌功能。
- `WorldZJH` 的锅底位置由 `s.table().pos()` 的单块中心计算，尚未消费整桌尺寸。
- 已有 `DDZTableLayoutTest`、`DDZMultiTableGameTest`、`tools/test_ddz_table_models.py`；当前未发现炸金花多方块拼桌专项测试。`CCDataPackGameTest.recipesAreLoaded` 仅检查两份配方是否加载，不能证明指定材料实际合成正确。

此前 HUD 报告中的两类桌子并排截图验证了颜色区分，未验证同类炸金花桌融合。此前测试通过的结论不能扩展成“炸金花拼桌已通过”。

## 2. 固定约定

从本次起固定深蓝斗地主、酒红炸金花；延续现有 PNG、木框和侧面牌标识，不继续试换颜色。每种游戏保持独立的方块、物品、配方及贴图资源标识。以后新增游戏增加自己的资源，不覆盖这两种游戏的配色。

配方最终目标固定如下，**斗地主蓝色地毯尚待下一步落地**：

| 玩法 | 固定桌面 | 固定地毯材料 | 其余材料及产出 |
| --- | --- | --- | --- |
| 斗地主 | 深蓝 | `minecraft:blue_carpet`×1 | 任意木板×3、木棍×2 → 牌桌×1 |
| 炸金花 | 酒红 | `minecraft:red_carpet`×1 | 任意木板×3、木棍×2 → 牌桌×1 |

酒红纹理以原版红色地毯作为材料代表，不要求贴图像素与原版地毯完全同色。保留 `C / PPP / S S` 的现有布局和配方 ID，不新增染色轮换配方。配方更新不改变已放置的桌子、现有物品或其存档 ID。

## 3. 后续实施顺序

### 第一步：配方与说明一次性收口

将斗地主配方的 `green_carpet` 改为 `blue_carpet`；炸金花保留 `red_carpet`。同步中英文 README 的材料与摆法说明，并增加实际合成断言：蓝色材料只得到斗地主桌，红色材料只得到炸金花桌，旧绿色材料不再合成斗地主桌。检查配方加载、产出数量和最终 JAR 内资源，构建后更新安装包与报告。完成这一步后，不再调整两桌颜色及合成材料。

### 第二步：抽出可复用的拼桌结构，再接入炸金花

以斗地主现有实现为基线，优先复用纯结构识别、尺寸、中心、边界距离和连接模型生成能力。将必须共享的部分改为与游戏无关的组件，保留两种游戏各自的会话、规则、配置和筹码结算；迁移时先保持斗地主行为不变并跑回归。

两种游戏采用同一结构约定：同高度、四向相邻、**同一注册方块类型**连接；斜角、上下及跨游戏不连接。整桌最多 9 格，完整矩形才允许使用；摆放时允许暂时不完整，拒绝放置导致超过 9 格的连接块。不同游戏相邻时分别保留外框。

将炸金花的所有动作统一路由到整桌西北角主坐标，任意组成块操作同一局，人数仍为配置的 2–6 人，不随方块数增加。配置复制到各成员，主坐标变化时继承配置；采用整桌最近边界校验距离。客户端快照补充整桌尺寸，锅底与相关桌面显示采用整桌中心。四向连接模型覆盖炸金花自己的酒红图集，消除内部木框，保留外圈木框。

### 第三步：处理结构变化和资金安全

扩建、合并、拆除或替换任意组成块时，结束受影响的原牌局，按炸金花现有取消流程退还本局投入并通知所有订阅者及配置编辑者，再允许重新入局。**不直接合并两局锅底，也不把结构变化当作玩家主动弃牌。** 离线退款继续走原有托管恢复路径，验证无遗漏、无重复退款。

配置继承沿用斗地主策略：西北角已有配置优先；新主块未配置时继承原成员配置；拆分出的合法矩形各自继承配置。配置锁不复制为多个有效锁，禁止用跨成员操作绕过锁。区块未加载时不强制加载，给出明确反馈并按既定结构清理规则处理活动会话。

### 第四步：测试与实机验收后发布

| 验收范围 | 必须验证的结果 |
| --- | --- |
| 配方 | 蓝色、红色正确产出对应桌；材料不能串用，旧绿色配方停用；资源正确打包 |
| 合法结构 | 1×1、1×2、2×3、3×3、1×9 及转置结构统一主坐标，任意成员操作同一局 |
| 非法与隔离 | L 形、缺角、超过 9 格不可使用；斜角、上下、跨游戏不融合 |
| 资金与配置 | 入场不重复扣款；任意成员拆除、扩建、两桌合并均正确退还；主块变化、配置锁和重启继承正确 |
| 显示与操作 | 内部木框消失、外圈完整、酒红连续无空洞；锅底居中，远端可入局；观战和所有动作可经任意组成块触发 |
| 回归 | 斗地主拼桌原测试保持通过；炸金花单块玩法、筹码托管与断线恢复保持通过 |
| 实机证据 | 两种游戏各检查单桌与多块桌，实际多人完成一局；截图逐张查看后记录结果；炸金花补 6 人布局验收 |

实施顺序固定为配方 → 共享结构与回归 → 炸金花会话及模型接入 → 资金与配置边界 → 实机截图复核 → 构建交付。各步骤完成后记录实际结果，不能把本计划中的目标写成已经完成的功能。
